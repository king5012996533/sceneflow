# 决策记录：不基于 DSH 接入 agent 运行时，改为自研

> **决策**：**放弃**把 DeepSeek Harness（DSH）用作服务端 agent 运行时，改为在现有基座上自研 agent 架构。
> **日期**：2026-09-20（晚，与 Phase 0 落地同日）
> **作废**：`docs/agent-runtime-plan-2026-09-20.md`（同目录，正文保留作历史与实测数据）
> **影响**：**产品代码零改动** —— DSH 从未进入本仓库（无 profile、无 persona、无 import），不需要拆任何东西。

---

## 一句话

DSH 是一栋要**另起地基**的附属楼（独立容器 + node ≥22.19 + 4G 构建内存），而它掌握的是**循环本体**；我们的产品规则——计费、额度门闸、画布写入权、记录归档、退款——全在楼外，每条规则都得跨边界投影一次。与其长期付这笔「投影税」，不如自己写循环。

## 决策依据

### 1. 基础设施硬约束（决定性的一条）

| 约束      | 现状 / 要求                                                                   | 结论                                                                          |
| --------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 线上内存  | 2G 机器：PM2 上限 1200M、Next 堆上限 768M，构建靠 swap 才不被 OOM killer 杀掉 | DSH 自建要 `--max-old-space-size=4096`；**一次 run 的内存占用就能把主站 OOM** |
| node 版本 | 线上 node 20.20.2（`deploy.sh` 只做 `npm install` + `node server.js`）        | DSH 要求 `^22.19.0 \|\| >=24.0.0`                                             |
| 安全边界  | DSH 能执行模型生成的命令，其 `SAFETY.md` 要求一次性容器                       | runner 不能与主站共享网络命名空间 → **必须另起容器，即另起一栋楼**            |

三条都来自本机实测（plan §3.1 / §1.3），不是估算。

### 2. 上游渠道风险

`latest` 指向 `0.1.5-rc.2`（连"稳定"通道本身就是 rc），`alpha` 指向 `0.1.6-alpha.2`；官方声明会有破坏性变更。锁版本只能挡住一半——替上游兼容性兜底的成本仍在我们这边，且是长期的。

### 3. 集成摩擦（本周实测，全部发生在边界上）

| 现象                                                   | 处置                                                                  | 状态                  |
| ------------------------------------------------------ | --------------------------------------------------------------------- | --------------------- |
| 工具确认与画布写入权门闸冲突，写入被拦                 | 关掉工具确认才通（`canvas-local-agent-panel.tsx` 在自动连接时直接关） | 绕开，未根治          |
| 写入权释放时机不当 → 连写随机丢笔                      | 改为写入完成即释放（commit `35730fe`）                                | 已修                  |
| 写后立刻读回拿到旧快照（agent 自检误判）               | 往 persona 里加规则兜                                                 | 绕开（prompt 层补丁） |
| 门闸超时后残留待确认卡片卡住后续写入；迟到批准仍会补写 | 待定                                                                  | 未决（见文末）        |

四处里**只有一处**（连写丢笔）是我们改自己的代码根治的；另外三处至今没根治——两处靠绕开（关掉工具确认、往对方 prompt 里塞规则），一处未决。这正是「在别人框架里投影我们的产品规则」的成本形态：**不会一次性付清，而是每加一条产品规则就再付一次**。

## 不做什么（本次决策的边界）

- **不拆代码**：产品仓库零 DSH 依赖，无需清理。
- **不影响已上线的另一条线**：画布右上角的「Agent」面板连的是 `@basketikun/canvas-agent`（我们自己的 npm 包），桥接用户电脑上的 **Codex / Claude Code**。它跑在用户本机、不吃服务器内存，与 DSH 无关，继续保留。
- **不丢数据**：作废的是施工依据，不是知识。plan 文档里的本机容量实测、渠道版本错位、遥测默认值、以及"为何不拿它的 Web UI 当主界面"的结论，自研时同样用得上。

## 替代方向：自研，但只新写「循环本体」

自研不是从零。已有的这些家底直接复用：

| 已有资产                                                                                   | 位置                                                                                                              |
| ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| 画布 run 锁与 run 语义（`tryClaimCanvasRun` / `canvasRunOwner` / `forceReleaseCanvasRun`） | `web/src/app/(user)/canvas/engine/scheduler/run-lock.ts`                                                          |
| 画布工具注册表 + schemas（单一注册表，31 个工具）                                          | `web/src/app/(user)/canvas/engine/tools/registry.ts`                                                              |
| 上游代理、额度门闸、密钥托管（平台 key / BYOK）                                            | `web/src/lib/generation/proxy-access.server.ts`、`upstream-endpoint-policy.ts`、`upstream-call-budget.ts`、凭证表 |
| 按 token 计费地基：usage 采集 + `settleTextTurnUsage` + 幂等流水                           | P0 系列，已上线                                                                                                   |
| 生成任务全链路：排队、轮询、归档、退款策略                                                 | `web/src/lib/generation/generation-jobs.server.ts` 等                                                             |
| 快照 / 备份状态模型（画布状态已有云端备份）                                                | `CanvasBackup` + 画布客户端                                                                                       |

**要新写的只有循环本体**：轮次状态机、工具派发、上下文管理与压缩、断点续跑、审批与反问的接缝，外加进程形态（按 run 起停、上下文落库、进程只做转发——这条能让 2G 的机器也扛得住，是自研相对整包 DSH 的结构性优势）。

## 什么情况下应该回头重新评估第三方 harness

不是"永远不用第三方"，而是给出可复评的触发条件：

1. 主机内存翻倍、或独立 runner 主机到位（§3.1 的第一条不再是硬约束）；
2. 上游出了**真正的稳定通道**（非 rc、有兼容性承诺与升级窗口）；
3. 我们自己的循环在「上下文压缩质量」或「长任务续跑」上撞到明显天花板，且自研成本已经超过投影成本。

## 未决与连带

- **门闸超时残留卡片导致后续写入卡死 + 迟到批准补写**：经查与本决策**无关**——它在我们自己的代码里（`canvas-local-agent-panel.tsx` 的待确认流程 + `engine/scheduler/run-lock.ts` 的写入权），超时是 agent 侧桥接层掐的（Codex 的 `tool_timeout_sec: 90`，见 `canvas-agent/src/agents.ts`）；本机 Codex 线开着工具确认时同样会碰。继续作为普通待办跟踪。
- **Phase 0 的计费地基（按 token 结算）**：与本决策无关，属于产品能力，继续保留并已被本机 Codex 线使用。
