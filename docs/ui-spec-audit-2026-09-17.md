# 视觉规格审计 · SceneFlow vs CanvasMind

日期：2026-09-17 ｜ 目的：把"他的 UI 好看"翻译成可执行的规格差异，判断"只换皮、保留手感"的路径
结论一句话：**他的好看不是因为数值整齐（他比你乱得多），而是因为「中性灰阶 + 单一强调色 + 发丝描边 / 透明分层」这四个方向决策。**

`@theme inline` 里 `--radius-sm/md/lg/xl = radius ∓ 4px`（globals.css:12–15），**并且额外覆盖了 `--radius-2xl/3xl/4xl`**（globals.css:45–47，`×1.8 / ×2.2 / ×2.6`）。以 `:root { --radius: 0.75rem }`（globals.css:51）代入：

| `rounded-md`   | `0.75rem − 2px` | **10px**   | 32   | 与 `rounded-[10px]` **完全重复**（4 处）                                                                                                    |
| `rounded-lg`   | `0.75rem`       | **12px**   | 83   | 事实标准，无冲突                                                                                                                            |

> **勘误（2026-09-17 实施时复核）**：本表初版写成 `rounded-xl` 与 `rounded-2xl` 同为 16px，**是错的**。2xl 走的是 `×1.8 = 21.6px` 而非 Tailwind 默认的 `1rem`。真正的**同值重名只有一处**：`rounded-md` 与 `rounded-[10px]`（都是 10px）。

**根因**：token 阶梯吐出 21.6 / 26.4 / 31.2px 这种小数，设计师不会拿它当基准，于是手挑整数像素，结果必然和 token 撞车（`[9px]`≈sm、`[10px]`=md、`[18px]`≈xl、`[26px]`≈3xl）。→ P3 不是"把 18 种收成 4 种"这么简单，得先把阶梯落到整数网格上。

### 那它的"精致"到底来自哪 → 四个方向决策

| #   | 它的做法                          | 具体证据                                                                                | 为什么有效                                                 |
| --- | --------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 1   | **纯中性灰阶**                    | token 全是 `hsl(0 0% 11%)`(0 饱和)、`hsl(0 0% 91%)`、`hsl(0 0% 50%)`                    | 灰阶 0 饱和 = 干净、专业、不脏；你的是绿灰                 |
| 2   | **单一高饱和强调色**              | `--primary: #009dff`（亮蓝），辅色也全是蓝色系 `hsl(204 100% 97%)` / `hsl(200 98% 39%)` | 只有一个重点，视线不打架；你有铜金 + 绿灰两套              |
| 3   | **发丝描边统一走带 alpha 的黑**   | `#00000014`（8% 黑）出现 **150 次**，是它的第一高频"颜色"                               | 描边永远比底深一档、永不"死黑"，边缘干净                   |
| 4   | **用白 alpha 做层级而不是多档灰** | `rgba(255,255,255,.04/.06/.08/.12)` 四个层级（深色区）                                  | 一套透明层表达所有层级，天然和谐；你是 44 种 rgba 各写各的 |

另外它画布区另有一套青蓝（`#00cae0`、`#6b8cff`）+ 玻璃模糊，属于"效果层"，是它的辨识度来源。

## 可执行结论

**优先级 ≠ 数值整齐度**，按"观感收益 / 改动成本"排序：

| 优先级 | 动作                                                                                                                                          | 改动面                       | 风险 | 预期收益           |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | ---- | ------------------ |
| P0     | **灰阶去绿**：`--background / --foreground / --border / --muted / --accent` 等约 20 个 token 换成 0 饱和中性灰                                | 只改 globals.css 的 token 段 | 极低 | 最大（治"脏"）     |
| P1     | **强调色收敛为一个**：铜金 `#a0713f` 降为品牌点缀（仅 logo/高光），功能强调色统一                                                             | token + 少量类名             | 低   | 大（治"重点不清"） |
| P2     | **阴影统一成同色温 3 档**（浮层/卡片/内凹），26 → 3                                                                                           | token + 逐组件替换           | 低   | 中                 |
| P3     | **圆角收敛 4 档**（6/10/14/999）并修掉 `xl==2xl`、`md==[10px]` 的重复命名                                                                     | token + 类名替换             | 低   | 中                 |
| P4     | **字号建 5 档阶梯**（10/11/13/15/20 + display），修 44px 以下 17 个任意值                                                                     | 类名替换                     | 低   | 中                 |
| P5     | **描边改发丝**：`border` 统一为 `rgba(0,0,0,0.06~0.08)` 一档                                                                                  | 类名替换                     | 低   | 中                 |
| —      | **不要动**：间距（已规整）、任何 `transition/animation` 时长与曲线、事件处理、节点 `width/height`、`pointer-events`/`z-index` 语义/`overflow` |                              |      | 动这五项才会丢手感 |

**换皮红线（守住就不会丢交互手感）**

1. 不改节点 `width/height`（连线端点来自节点数据里的尺寸，改了会看起来错位）
2. 不碰 `transition` / `animation` 的时长与曲线
3. 不碰 `pointer-events` / `z-index` 语义 / `overflow`
4. 不碰任何事件处理函数
5. 只改颜色、描边、圆角、阴影、字号、间距

**技术前提（已核实）**：`canvas-connections.tsx` 零 DOM 测量，端点由节点数据 `width/height` 计算；交互对 DOM 几何的 27 处依赖全是弹层定位 / 小地图 / 输入光标 / 视口尺寸，与拖拽、连线数学无关。→ **外观与交互是解耦的，"只换皮"结构性可行。**

## 下一步可选路径

- **路径一（推荐，低风险）**：只做 P0 + P1 —— 灰阶去绿、强调色收敛。改 token 为主，一屏一屏验证（截图 + 拖拽/连线/输入冒烟），随时可回滚，品牌性格不变。
- **路径二（中风险）**：借他那种"深色玻璃 + 青蓝"的方向。观感变化最大，但所有屏都要过一遍、浅色场景要重新校色、品牌从"暖色编辑风"变成"科技玻璃风"。

两条路都不需要碰交互逻辑。

# 实施记录：P0 + P1 已落地（2026-09-17）

用户选择**路径一（P0 + P1）**。P2–P5 **未做**，见文末"剩余工作"。

## 一个必须先纠正的前提

审计时的假设是"改 token 层就够"。**实测不成立**：shadcn 那套 token 几乎没人用——`bg-primary` / `text-primary` / `bg-muted` / `bg-card` / `bg-secondary` 在 164 个文件里用量为 **0**，只有 `bg-background`(9)、`text-muted-foreground`(3)、`border-border`(2) 和几处 `var(--x)`。

**界面是被硬编码 hex 类名画出来的。** 所以 P0/P1 只能做成**组件层的机械色值重映射**，改 token 只是顺带。这决定了后面的所有取舍。

## 怎么做的

两个确定性脚本，都支持 `--dry-run`，且**每条规则执行前断言精确出现次数**，数量不符立即中止（防止误伤同名色值）：

### P0 · 灰阶去绿（`remap.py`）

输入 50 个 hex 种类 + 6 组 rgba + 10 个 oklch 值。四条硬保证：

| #   | 保证                                                    | 为什么                                                                                                                                |
| --- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **保持 HLS 明度不变**                                   | 只动色相，不动明暗关系                                                                                                                |
| 2   | **色相统一旋到 30°**                                    | 暖色编辑风的锚点                                                                                                                      |
| 3   | **彩度上限随明度变化**（暗端 2% → 中调 5% → 亮端 1.5%） | 统一封顶会把深灰染成"棕黑"。真实暖灰阶就是这个形状（Tailwind stone 暗端 `#0c0a09` 仅 1.2%、中调 `#78716c` 4.7%、亮端 `#f5f5f4` 0.4%） |
| 4   | **对比度守护**                                          | 暗到能当文字的颜色（白底对比度 ≥ 2.5）重映射后不许掉对比度，必要时回退明度                                                            |

白名单保留：语义色（成功/错误/警告）、分类色（节点类型 `NODE_COLORS`、画布 `type.*`、小地图、图表色板）、铜金家族、`DiaTextReveal` 装饰渐变。

**外部验证**：这个变换独立收敛到 Tailwind 的 stone 阶梯（`#6b7280→#77716b`≈stone-500、`#98a2b3→#a5a19c`≈stone-400、`#fa…→#f9f7f5`≈stone-50），而且代码库里本来就有的骨架屏渐变 `#78716a` 正好落在这条线上。

### P1 · 强调色收敛（`accent.py`）

37 条规则 / 14 个文件，逐条断言命中数。要点：

- `--primary` / `--sidebar-primary` → `#a0713f`；`--ring` → `rgba(160,113,63,.35)`；暗色镜像 `#c08e4f` / `rgba(192,142,79,.35)`
- `.ant-btn-primary`（globals.css 两处）→ 铜金
- `app-theme.ts`（`colorPrimary` / `primaryHover` / `tableSelected*` / `selectSelectedBg`）、`canvas-theme.ts` 的 `activeStroke`、`sceneflow-theme.ts` 的 `hoverBorderColor`、workbench 的 `--accent` / `--accent-deep` / `--accent-soft` → 铜金族
- 清掉**第三、第四个强调色**：`#a8afff`（禁用的主按钮，靛蓝）→ 中性 `#cdc9c5`；`#4f46e5`×2、`#2f80ff`（选择态，变量名从 `selectionBlue` 改为 `selectionAccent`）、mention chip、`#c7d2fe` 悬停、`#cfc8ff` 虚线框 → 铜金或中性
- 顺带拔掉两处"潜藏的蓝"：`credit-balance-card` 的 `hover:bg-[#3846e8]` 和 `rgba(79,93,255,.18)` 阴影

**为什么铜金是正确的收敛方向（不是拍脑袋）**：`.sf-mag` 里它叫 `--terra`、`.sf-landing` / `.sf-login-page` 里叫 `--sf-red`，landing 页有 **17 处** `color: var(--terra)`——铜金当文字色本来就是既有品牌语言。真正的问题是 sage 灰被误提拔成了"功能主色"，于是两个浊色系互抢重点。

### 收尾：正则盲区补扫（第三遍）

第一遍的重映射正则是 `#[0-9a-fA-F]{6}\b`。**`\b` 在 `_` 前不成立**（`_` 是 word 字符），所以 Tailwind 任意值里紧贴下划线的色值**全部漏扫**：

```
bg-[linear-gradient(135deg,#fbf7ef_0%,#f7f3ea_48%,#eef4ff_100%)]
                                          ↑ 这里永远匹配不到
```

全库共 17 处漏扫（5 个色值）。其中 `#fbf7ef` / `#f7f3ea` / `#f9f3e8` / `#f5ecdd` / `#f2e9da` 本来就是暖色（**漏了也无害**），只有渐变尾色 `#eef4ff`（冷蓝白）是真问题——奶油色渐变最后一段突然转冷，正是 P0 要治的"脏"。

同时两处中性色因为**阈值外**被跳过：`#746b7a`（色相 276°，超出 70–260° 窗口）和 `#050816`（饱和度 0.63，被当成饱和蓝）。两者都是纯中性用途（静音文字 / 悬停文字）。

补扫把它们按同一套规则归拢到既有暖色阶上（优先取代码库里已有、用量大的值，而不是新造）：

| 原值                                    | 新值      | 落点依据                  | 处数 |
| --------------------------------------- | --------- | ------------------------- | ---- |
| `#746b7a` 紫调灰（日志 / 加载提示文字） | `#726d67` | 全库主静音灰，已用 109 处 | 3    |
| `#050816` 蓝黑（悬停文字）              | `#1b1814` | 既有暖墨，已用 17 处      | 2    |
| `#eef4ff` 渐变冷尾                      | `#f9f7f5` | stone-50 档，已用 26 处   | 4    |
| `#e5e7eb` 点阵冷灰                      | `#eceae7` | 既有暖灰，已用 21 处      | 2    |

## 结果

### 静态指标（同一把尺子，164 文件 / 30,083 行）

| 维度     | 改前           | 改后     | 判断                         |
| -------- | -------------- | -------- | ---------------------------- |
| hex 种类 | 96             | **89**   | ↓7（其余维度按设计完全没动） |
| hex 处数 | 551            | 551      | 不变（纯替换，不增删）       |
| rgba     | 91 处 / 56 种  | 91 / 56  | 不变                         |
| 阴影     | 73 处 / 26 种  | 73 / 26  | 不变（P2 范围）              |
| 圆角     | 306 处 / 18 种 | 306 / 18 | 不变（P3 范围）              |
| 字号     | 524 处 / 24 种 | 524 / 24 | 不变（P4 范围）              |
| 间距     | 2 处任意值     | 2        | 不变（本来就干净）           |

**诚实说明**：种类数几乎没动。变的不是"数量"而是"方向"——改后所有中性色坐在同一条暖灰阶上。CanvasMind 自己的 hex 种类是 286 种（比我们乱 3 倍），它的精致来自方向一致，不是数值整齐。这也说明 P0 的收益**不能**用"种类数下降"来衡量。

前 5 高频色（处数）改前 → 改后：

| 改前      |     | 改后      |        |
| --------- | --- | --------- | ------ |
| `#67726b` | 94  | `#726d67` | 97     |
| `#dde2dc` | 71  | `#e2dfdc` | 71     |
| `#2a3330` | 61  | `#a0713f` | **62** |
| `#ffffff` | 50  | `#332f2a` | 61     |
| `#a0713f` | 50  | `#ffffff` | 50     |

铜金从第 5 位升到第 3 位（50 → 62 处），且不再与 sage 平起平坐——**这正是 P1 想要的效果**：一个重点，而不是两个。

### 运行时色板（真实渲染出来、去重后的颜色）

在编辑器里建 2 个节点、拖拽、连线，然后统计所有可见元素的计算样式色值，按是否带绿判定：

| 场景        | 带绿的颜色种类 | 背景       | 描边      | 连线   |
| ----------- | -------------- | ---------- | --------- | ------ |
| 浅色 · 改前 | **7 / 13**     | 7 / 11     | 6 / 9     | 6 / 11 |
| 浅色 · 改后 | **1 / 13**     | 1 / 11     | 1 / 9     | 1 / 11 |
| 深色 · 改前 | 6 / 12         | **8 / 10** | 5 / 7     | —      |

## 改动规模与一个坑

最终 **48 个文件 / 539 增 / 539 删**——全部是行内替换，零结构改动。

> **踩坑记录（换皮类机械改动的通用陷阱）**：脚本用 Python 读写文件时，`open(..., encoding="utf-8")` 读 + 默认写会把原文件的 **CRLF 换成 LF**。本仓库没有 `.gitattributes`、`core.autocrlf` 也未设置，文件存什么就是什么。结果 6 个文件（2 个纯 CRLF、4 个混合换行）被整体重写，diff 从 539 行虚增到 1803 行，且整个文件显示为全改。
>
> 修复方式：编辑不增删行 → 按**行号**逐行套用 HEAD 的换行风格还原，行内容照旧。已核对还原后 diff 回到 539 行级别，且改动内容一字未丢。**下次做这类批量替换，先按二进制读、按二进制写，或先读一次保存换行风格。**

## 部署时踩到的第二个坑：构建成功 ≠ 令牌层真的换了

第一次部署看起来完全成功：`git pull` 到 `c598d21`、构建通过、PM2 重启、PM2 列表里 uptime 归零。但**线上算出来的 token 还是旧的**。

### 怎么发现的

用 curl 直接读线上 CSS，看到 `:root{--radius:.75rem;--border:#dde2dc;--ring:#75827c59;--primary:#75827c;--background:#f4f6f2…}`——全是 sage 旧值。而在服务器上 `grep 'primary:#a0713f' .next/static/chunks/*.css` **一个文件都命中不到**。

诡异的是同一个 chunk 里**新旧混杂**：手写 CSS 段（`:root`、`.sceneflow-* .ant-modal-content`、`.ant-btn-primary`）是旧的，而 Tailwind 按类名生成的工具类（`.border-\[\#e2dfdc\]`、`.bg-\[\#e2dfdc\]`）是新的。

而服务器源码是对的：`src/app/globals.css` 里旧值 0 处、新值 12 处；全仓库（排除 `node_modules`/`.next`）搜旧值**一个文件都没有**。旧内容只存在于两处：`.next/cache/turbopack/**/*.sst`（构建缓存，2.2G）和那个已产出的 chunk。

### 根因与修复

Turbopack 的持久化缓存吐回了**过期的 globals.css 编译单元**。修复：

```
rm -rf /root/infinite-canvas/web/.next/cache     # 只删构建缓存
bash deploy.sh                                    # 冷构建 + 重启
```

只删 `cache`（不删整个 `.next`）是为了让运行中的进程不受影响——删完立刻 `curl 127.0.0.1:3003/canvas` 仍是 **200**。

重建后：旧 `primary:#75827c` 在 0 个 chunk 里，新 `primary:#a0713f` 落在 `1hqp-o6q0bfg_.css`，`dde2dc` 0 处 / `e2dfdc` 23 处。

**关键细节**：chunk **文件名变了**（`1b8ixfw2ozn14` → `1hqp-o6q0bfg_`）。这点很重要——这些资源带 `cache-control: public, max-age=31536000, immutable`，如果文件名不变而内容变，已经访问过的浏览器**永远**拿不到新 CSS，且无法远程清除。

### 教训

对"纯换皮"这种**收益全在 token 层**的改动，**必须校验线上的计算样式**：构建通过 + PM2 重启 ≠ token 真的换了。建议在部署流程末尾固定加一条断言——拉取线上 CSS，确认 `--primary` 等于预期值、且旧值在任何 chunk 里 0 命中。否则这次就会带着"部署成功"的结论交付一个一半还是 sage 的线上环境。
